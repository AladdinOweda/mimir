Mimir Browser — Engineering Wireframes Specification

الإصدار: Engineering Wireframes – 17 Core Screens

الغرض: تحويل مواصفات Browser UX السابقة إلى مرجع هندسي واضح لبناء الواجهات، مع الحفاظ على استقلال Browser Engine عن Universal Kernel، وعدم اختراع سلوك يخالف العقود المعتمدة.

نطاق هذه الوثيقة: الشاشات الأساسية الـ17 الواردة في مواصفة Browser UX. هذه مخططات هندسية وصفية وليست ملفات Figma أو قياسات نهائية مستخرجة من تصميم مرئي معتمد. القيم أدناه هي أساس تنفيذ أولي قابل للضبط من Design Tokens.

───

1. القواعد الهندسية المشتركة

1.1 إطار القياس المرجعي

استخدم Android Mobile كمرجع أساسي، مع اعتماد وحدات "dp" للمسافات والأحجام، و"sp" للنصوص.

الخاصية| القيمة المرجعية
عرض الهاتف المرجعي| 360dp
عرض الهاتف الصغير| 320dp
عرض الهاتف الكبير| 430dp
الهامش الأفقي الأساسي| 16dp
شبكة المسافات| مضاعفات 4dp
المسافة بين المجموعات| 16dp
المسافة داخل المجموعة| 8dp
ارتفاع شريط العنوان| 56dp
ارتفاع شريط التنقل السفلي| 64dp
الحد الأدنى لهدف اللمس| 48×48dp
نصف قطر البطاقات الأساسي| 16dp
نصف قطر الحقول| 12dp

هذه قيم مرجعية أولية، ويجب أن ترتبط بـ Design Tokens بدل توزيع أرقام ثابتة داخل مكونات الواجهة.

1.2 قواعد تقسيم الشاشة

الهاتف:

• منطقة النظام العلوية: Safe Area.
• Header ثابت أو قابل للطي حسب الشاشة.
• منطقة المحتوى: قابلة للتمرير عموديًا.
• Bottom Navigation يظهر في صفحات Browser الرئيسية، ولا يظهر في وضع تصفح الصفحة عندما تكون مساحة العرض الكاملة مطلوبة.
• Composer أو شريط العنوان يثبت في الموضع المحدد وظيفيًا، ولا يغطي المحتوى.

التابلت:

• الحفاظ على بنية الهاتف، مع تحويل القوائم المناسبة إلى لوحات جانبية.
• استخدام عمودين أو ثلاثة عندما يزيد ذلك وضوح العمل.
• عدم تكبير العناصر الصغيرة لمجرد توفر المساحة.

سطح المكتب:

• Sidebar ثابت أو قابل للطي.
• Main Workspace مرن.
• Inspector/Details Panel يظهر عند الحاجة.
• لا تترك المحتوى يتمدد بعرض الشاشة كله عندما يتطلب قراءة مركزة.

1.3 مناطق الشاشة القياسية

المنطقة| الاستخدام
System Safe Area| تجنب التداخل مع شريط النظام
App Header| عنوان الشاشة، الرجوع، البحث، الإجراءات
Primary Content| المحتوى الأساسي
Contextual Panel| التفاصيل أو الأدوات المرتبطة بالعنصر المحدد
Bottom Action Area| إجراء أساسي أو Composer عند الحاجة
Bottom Navigation| الانتقال العام بين مساحات التطبيق

1.4 قواعد الحالات العامة

كل شاشة تفاعلية يجب أن توثق وتنفذ الحالات التالية بحسب انطباقها:

• Initial: الحالة الأولى قبل تحميل البيانات.
• Loading: تحميل مع مؤشر واضح، دون تجميد الواجهة كلها.
• Empty: لا توجد بيانات، مع توضيح الإجراء التالي.
• Content: عرض البيانات.
• Error: خطأ قابل للفهم مع إجراء استعادة مناسب.
• Offline: انقطاع الشبكة مع تمييز الوظائف المتاحة محليًا.
• Permission Required: الإذن مطلوب قبل تنفيذ العملية.
• Restricted: العملية ممنوعة وفق سياسة أو صلاحية.
• Partial: بعض البيانات متاحة وبعضها لم يكتمل.
• Selection: عنصر أو أكثر محدد.
• Disabled: إجراء غير متاح مع توضيح السبب عند الحاجة.

لا يجوز استخدام حالة Empty بدل Loading، ولا إظهار نجاح عملية قبل تأكيد نتيجتها من المحرك.

المواصفات الهندسية

• Header بارتفاع 56dp.
• حقل البحث/العنوان بعرض المحتوى ناقص الهوامش، وارتفاع مستهدف 52–56dp.
• Quick Actions: عمودان على الهاتف، وتتحول إلى صف أو شبكة أوسع على التابلت.
• Recent Tabs: بطاقات مضغوطة، لا تعرض تفاصيل زائدة.

• لمس حقل العنوان يفتح إدخال URL أو البحث.
• New Tab ينشئ تبويبًا جديدًا ثم يفتح Browser Workspace.
• AI Assistant يفتح Browser AI Home.
• بطاقة تبويب تستعيد التبويب وحالته إن أمكن.
• More في البطاقة يفتح قائمة إجراءات التبويب.

المواصفات الهندسية

• قائمة عمودية قابلة للتمرير.
• كل بطاقة تبويب تتضمن Preview، عنوانًا، Domain، حالة التبويب.
• زر الإغلاق مستقل عن فتح البطاقة.
• حالة التبويب (Loading/Ready/Suspended/Crash) تظهر بعلامة نصية أو أيقونة مفهومة.
• البحث يرشح التبويبات دون حذفها.
• التحديد المتعدد يتيح إجراءات جماعية.

• الضغط على البطاقة يعيد التبويب إلى Workspace.
• الإغلاق يطلب تأكيدًا عند وجود عملية نشطة غير محفوظة أو حالة تستوجب ذلك.
• New Window ينشئ نافذة وفق قدرات المنصة.
• Suspend/Resume لا يغيّر ملكية التبويب أو عنوانه.
• إغلاق تبويب مرتبط بمهمة AI لا يعني إلغاء المهمة تلقائيًا؛ يجب إظهار أثر الإغلاق وخياراته.

• لا يساوي طلب المستخدم "اشرح الصفحة" إذنًا بالنقر أو الإرسال أو الشراء.

3. قواعد التحويل إلى التابلت وسطح المكتب

الهاتف

• عمود واحد للمحتوى الأساسي.
• قوائم التفاصيل تظهر كشاشات أو Bottom Sheets.
• لا يقل هدف اللمس عن 48dp.
• لا تستخدم تقسيمًا أفقيًا إذا أدى إلى ضغط المحتوى.

التابلت

• يمكن استخدام عمودين في Multi-Model Workspace وTabs Manager وSettings.
• Inspector يظهر بجانب المحتوى عند الحاجة.
• يمكن إبقاء شريط التنقل العام مع توسيع Labels.
• لا تُعرض ثلاثة أعمدة إلا إذا كان لكل عمود مساحة قراءة كافية.

سطح المكتب

• Sidebar للتنقل.
• Toolbar خاص بالمساحة.
• Workspace مركزي.
• Inspector اختياري.
• دعم لوحة المفاتيح والاختصارات.
• عدم ربط تصميم Desktop بتكبير تصميم الهاتف فقط.

5. شروط قبول المخططات قبل التنفيذ

لا تعتبر المخططات جاهزة للتنفيذ النهائي حتى تتم مراجعة:

1. توافق كل شاشة مع Design Tokens المعتمدة.
2. مطابقة التنقل مع UX Interaction Specification.
3. تعريف حالات Loading/Empty/Error/Offline/Permission.
4. اختبار RTL وLTR.
5. اختبار عرض 320dp و360dp و430dp.
6. اختبار التابلت وسطح المكتب.
7. اختبار إمكانية الوصول والتباين وتكبير الخط.
8. التأكد من عدم وجود أزرار شكلية بلا Actions حقيقية.
9. التأكد من أن كل إجراء مرتبط بعقد Browser/Kernel صحيح.
10. توثيق كل اختلاف عن المواصفات السابقة قبل اعتماده.

6. حدود هذه الوثيقة

هذه الوثيقة تغطي المخططات الهندسية الوصفية للشاشات الـ17 الأساسية. وهي لا تدعي أنها أنشأت ملفات تصميم رسومية أو أثبتت التنفيذ الفعلي.

وتوجد شاشات إضافية سبق تحديدها ضمن التوسعة المعمارية للمتصفح، وهي:

• Private Browsing / Incognito.
• Extensions Manager.
• Developer Tools.
• Browser Diagnostics.

يجب إعداد مخططاتها الهندسية أيضًا قبل اعتبار تصميم Browser كاملًا، كما يجب استكمال العقود والاختبارات والتكاملات الموضحة في خطة إكمال المحرك.

قاعدة الاعتماد: لا تُعدّل أي ADR أو عقد قائم لمجرد مطابقة المخطط؛ يجب أولًا مراجعة المرجع المعتمد، ثم تعديل المواصفة أو العقد وفق مسار الحوكمة.
